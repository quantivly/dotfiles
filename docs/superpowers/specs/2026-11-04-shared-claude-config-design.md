# Shared Claude Code configuration across hosts — design

**Status:** approved by Zvi 2026-11-04 (brainstorm, builder check and his eight answers recorded below). Implementation plans: docs/superpowers/plans/2026-11-04-claude-config-audit.md (steps 1–2), docs/superpowers/plans/2026-11-06-claude-memory-stores.md (step 5), later plans per step.

## Context

Zvi runs Claude Code interactively on the laptop (cilantro) and, through herdr's machine
sidebar, on remote hosts. The laptop's configuration (settings, hooks, skills, plugins, the
user-level CLAUDE.md, auto-memory) grew with the dotfiles repo and a private overlay; the
remotes got hand-copied slices at different times, so each host drifts on its own. Zvi's
account of the pain: skills and plugins missing remotely, memory not carrying over,
settings/hooks/permissions behaving differently, and general drift with no single incident.

The intended outcome: one declared configuration, in git, that every agent host renders
for itself and keeps level on its own timer, with memory shared both ways, and a doctor
on each host that says whether the live config is the declared one.

Decisions Zvi gave on 2026-11-04:

1. **Hosts that count: laptop, dev, sol-build.** nanoclaw leaves herdr and becomes
   production-only (6 agent sessions since mid-September; it hosts Sol's service).
2. **Memory carries over in full:** per-repo project memories, the user/feedback memories
   about how Zvi works, and two-way (a memory written on a remote reaches the other hosts).
3. **The private overlay travels as a per-tenant slice:** dev gets the quantivly pieces,
   sol-build the personal ones (plus quantivly: nanoclaw is a shared personal/Quantivly
   project). Secrets never move; they stay hand-placed.
4. **Which seat sol-build bills does not matter.** Multi-account-per-server is planned
   work elsewhere (the `seats/<seat>.env` token layout that dev-sync and claude-oauth-store
   are "ready for, not using yet"; DO-666), so this design stays account-agnostic.

## What exists and is reused

- `scripts/dev-sync` + `systemd/dev-sync.timer` (armed on dev, daily): keeps dotfiles at
  `origin/main`, Claude Code at latest, herdr/herdr-draft level, work plugins enabled,
  clones fetched; ✓/✗/⚠ rows, `--check`/`--apply`, a state table of 325 checks. This is
  the proven "a remote keeps itself level from git" loop and the base for every host.
- `scripts/herdr-claude-wire.sh`: idempotent jq merger into `~/.claude/settings.json`
  (statusLine, Stop bell), regenerates the herdr skill, runs `herdr integration install`.
- `scripts/claude-account-dirs.sh`: the laptop's per-seat dirs; `claude-account-dirs.data-entries`
  names the shared set (`projects plugins skills hooks CLAUDE.md`).
- `install.conf.yaml` `link:` entries for hooks and skills; `install.conf.herdr.yaml` for
  the modular `--herdr` install.
- `~/.dotfiles-local`: tenants table, tenant-root CLAUDE.md files, overlay hook,
  `scripts/check-links.sh` (every declared link must be a symlink into the checkout),
  `rabota/` machine and tenant config.
- `scripts/redact-secrets.sh`, `scripts/scrub-transcript-secrets.py`, the secret-emission
  guard: the secret rules the memory sync reuses.
- `scripts/server-bootstrap.sh` is **not** reused: it has no Claude Code step, DO-635
  rejected it for dev, and the repo inventory found its server-template phase never runs
  (`./install` creates `~/.zshrc.local` first). Filed as its own issue (filed as DO-881), not fixed here.

## Design

### D0. Audit and merge first: no host is overwritten until its better parts are in git

The laptop is not assumed to hold the best version of anything. Each host has pieces the
others lack or have let go stale, and the first render or sync would silently replace
them. Known examples from the probes:

- dev's `settings.json` has a `permissions.allow` list (13 rules: docker, curl, lsof,
  `npm run lint`…) disjoint from the laptop's 17; both are wanted. Its
  `autoMode.environment` org-wide half was generated against the real work repo
  (Quantivly, `quantivly-dockers`, terraform scopes, `.envrc` locations) and is the better
  text for the quantivly overlay, while the laptop's was generated against `/home/zvi`
  with no remotes and is wrong.
- dev's user-level `CLAUDE.md` ("Zvi's Instructions", 2026-02-02) carries Python,
  documentation, Linear and git-workflow rules that the laptop's newer file may have
  dropped rather than superseded; sol-build's is a hand excerpt of the laptop's. Three
  versions, one canonical file to produce.
- dev's 15 `~/.claude/agents` (2025) and `review-pr` skill (2026-02) predate the
  `pr-review-toolkit` and `code-review` plugins; some may still be worth keeping as
  dotfiles-local agents. They are audited, not deleted.
- dev's 7 memory stores (ci, sre-core, .github, operations-insights, dotfiles, hub,
  platform) hold facts written only there; the laptop's 24 stores hold the rest. The
  merged work store must contain both, with contradictions surfaced rather than
  resolved by whichever copy was read last.
- `~/Projects/CLAUDE.md` on nanoclaw and sol-build are hand-written host rule files
  (session caps, `suite-slot`, production boundaries) that belong in dotfiles-local as
  host-specific root variants, not lost when the hosts are re-pointed.
- Hook and skill copies differ by version (`herdr-agent-state.sh` v10 on the laptop vs
  dev's 2026-09-20 copy; the `herdr` skill), and the plugin sets differ (laptop 24
  entries, dev 4 enforced plus 2025 project-scope leftovers).

**Method.** New `scripts/claude-config-audit.sh`, run from the laptop, read-only on every
host:

1. `--collect`: over ssh, copies each host's config artifacts into a durable audit
   workspace, `~/Projects/handoffs/2026-11-claude-config-audit/<host>/` (laptop included,
   from `~/.claude` and every account dir's real files): `CLAUDE.md`, `settings.json`,
   `settings.local.json`, `keybindings.json`, `hooks/`, `skills/` (minus `synced/`),
   `agents/`, `plugins/{known_marketplaces,installed_plugins}.json`, every
   `projects/*/memory/`, the tenant-root and host `CLAUDE.md` files, and the repo-local
   `.claude/` dirs of checkouts both hosts have. Everything passes through
   `scripts/redact-secrets.sh` on the way in; credential files, `.claude.json` and
   transcripts are never collected.
2. `--matrix`: one row per artifact × host: identical / only-on / newer-on / conflict,
   with sizes, mtimes and, for JSON, per-key diffs (`permissions.allow` as set
   differences, `hooks` by basename, `enabledPlugins` by name). Memory stores are
   compared per topic file by name and content, and per fact by frontmatter
   `description`, so two files that state the same fact under different names are
   flagged alongside two files of one name with different bodies.
3. **Merge rules**, applied artifact by artifact and recorded with provenance (host,
   mtime, why) in `audit.md` beside the matrix: host-specific content goes to a host
   profile or host-root variant; a strict superset wins; sets are unioned; a conflict
   is merged by hand into a proposed file that Zvi reviews in the PR; a stale duplicate
   retires only once its content is confirmed present elsewhere or deliberately dropped.
   For memory: union by file name, regenerate each `MEMORY.md` index from the files'
   frontmatter rather than by text union, keep both bodies as `<name>.<host>.md` on a
   conflict and list them for review, and leave host-specific paths in facts as they
   are (they are evidence, and the reader is an agent on that host).
4. The merged canonical versions are what steps 2–4 commit. The first
   `host-sync --apply` on any host runs only after the audit PR has landed and every
   host's collected copy sits in the audit workspace, so nothing is lost even if a
   merge decision was wrong.

After the migration the same script's `--matrix` is the cross-host drift report run
from the laptop: `host-sync` says whether one host matches git, the audit says whether
the hosts still match each other.

### D1. Source of truth is git; every host pulls

Three repos, each with one job:

| repo | holds | why there |
|---|---|---|
| `quantivly/dotfiles` (public) | mechanism and team-safe config: hooks, public skills, the `dotfiles` marketplace, the settings **base** fragment, the render/sync/doctor scripts, systemd units | the team repo ships mechanism |
| `ZviBaratz/dotfiles-local` (private) | Zvi's data: user-level `CLAUDE.md`, `keybindings.json`, `zvi-voice`, the comms hooks, tenant table, tenant-root CLAUDE.md files, per-tenant settings **overlays**, rabota config, host profiles | personal, not secret, not for teammates |
| memory repos (private, new; one per tenant boundary, see D7) | auto-memory, keyed by repo identity | churns every few minutes; must not pollute the config repos' history; work memory must not sit in a personal repo nor personal memory on dev |

Secrets (`~/.zshrc.local`, `~/.config/claude-oauth/`, clauth's store) stay hand-placed,
as today. No host pushes file contents to another over ssh: the laptop is often asleep, and
the auto-mode classifier refuses remote shell writes. Each host runs the same timer against
git.

`~/.dotfiles-local/hosts/<name>.toml` (new) declares per host: tenants served, plugin
set, repo roots, whether herdr-draft is wanted, auth layout. Today's facts:

|---|---|---|---|
| laptop | quantivly, personal, toysim | clauth seats | account dirs, as today |
| dev | quantivly | long-lived token (quantivly-0) | shared with the team's stack; `agents.slice` caps; Zvi is its only Claude Code user (2026-09-15 handoff), so `~/.claude` is his |
| sol-build | personal only (Zvi, Q2: no work marketplace, no work credentials) | `/login` (quantivly-3, Zvi: "doesn't matter") | no sudo for `sol`; root steps are one-off and handed over. Measured 2026-11-04: as `sol` only herdr and bash run, no user units, no crontab; the GitHub runner is a separate `ghrunner` user. So `~/.claude` there serves only Zvi's herdr-spawned sessions and is the right config dir |
| nanoclaw | none | — | leaves herdr (D10) |

The tenant → machine seat table in `claude/tenants.zsh` and `[machines.*]` in rabota's
config already exist; the host profile points at them rather than restating seats.

with `{"tenants": [...]}`, read with jq; a host selects its profile through the marker file
`~/.config/claude-host-profile` (one line, the profile name), and that marker is what gates

### D3. One layout on every host

`<config dir>/CLAUDE.md`, `keybindings.json`, `hooks/*`, `skills/*` are dotbot symlinks
into the two checkouts (public and private `install.conf.yaml`); `settings.json` is
**rendered** (D4); `projects/<key>/memory` are symlinks into the memory checkout (D7).
On the laptop the config dir is each seat's account dir, which already links those names
to `~/.claude`; on dev and sol-build it is `~/.claude`. Nothing in this layout depends on
how the host authenticates. Skill entries as symlinks and `@path` imports in the
user-level CLAUDE.md are documented behaviour (`skills.md`, `memory.md`); shell-form hooks
run under `sh -c`, so `$HOME` in a hook command expands on every host. Per-host
configuration is unavoidable: no documented mode (Desktop SSH, Remote Control, cloud
sessions) runs the laptop's config against a remote filesystem.

### D4. `settings.json` is rendered from fragments, with `$HOME` paths

New `scripts/claude-settings-render.sh` (dotfiles), run by `./install` and by the sync
**only when the host's marker file `~/.config/claude-host-profile` exists** (D2): teammates who install the public repo through dev-setup, and modular
`--herdr` adopters, never have their `settings.json` rewritten. For them
`herdr-claude-wire.sh` stays as it is, foreign-statusLine refusal included. `base.json`
therefore holds only what the repo itself owns; model and effort defaults are overlay data.

1. Reads `claude/settings/base.json` (public): the repo's own hooks (secret guard, Stop bell,
   statusLine, herdr `SessionStart`, herdmates hooks) written as `$HOME`-relative commands
   (the secret guard's `f="$HOME/..."; [ -r "$f" ] && exec bash "$f"; exit 0` shape, which
   already works on dev), `extraKnownMarketplaces` (`quantivly` as a `github` source, never
   the `github-work` ssh alias; `dotfiles` as a directory source under `$HOME`), the
   `linear-key` plugin, `modelSettings`/`effortLevel` defaults.

   **Amended 2026-11-05 (DO-884):** the `quantivly` marketplace
   (`extraKnownMarketplaces.quantivly`) is declared in the quantivly tenant overlay
   (`claude/settings/quantivly.json`), not in `base.json`; base keeps only the `dotfiles`
   directory marketplace and `linear-key`. Reason: Zvi's Q2 (sol-build is personal-tenant
   only; no work marketplace there). Source: `~/Projects/handoffs/2026-11-claude-config-audit/audit.md` "Not decided here".
2. Overlays `~/.dotfiles-local/claude/settings/common.json` and
   `claude/settings/<tenant>.json` for each tenant in the host profile: `permissions.allow`,
   `permissions.defaultMode`, `enabledPlugins`, the comms hooks, the toysim live-store
   guard (toysim tenant only), theme, model, `agentPushNotifEnabled`.
3. Merges into the live file with jq: lists are unioned, objects deep-merged, scalars taken
   from the highest fragment; keys the fragments do not declare are left exactly as found
   (`autoMode.environment` is machine-specific text; `env` belongs to clauth;
   `feedbackSurveyState` and friends belong to Claude Code). Writes by temp file + rename,
   backs up the previous file, refuses a symlink (dev-sync's `here_plugins` already does
   this). `--check` prints the diff and exits 1; `--print` shows the result.

   **Amended 2026-11-05 (DO-884):** (a) the renderer replaces only the `### Org-wide` block of
   `autoMode.environment` (the lines from `### Org-wide` up to, not including,
   `### User-specific`) from the tenant overlay; the `### User-specific` half of the live
   array is left exactly as found. (b) Hooks are keyed by the basename of the first script
   path in the hook command (`$HOME/...` or `/...`), or by the executable when the command
   has no path (`herdmates hook …`); a rendered entry REPLACES the live entry with the same
   key under the same event; an event no fragment declares is left as found. This is what
   makes dev's `/home/ubuntu` SessionStart entry and the comms hooks' unguarded entries get
   replaced rather than duplicated. Source: `~/Projects/handoffs/2026-11-claude-config-audit/audit.md` "Not decided here".

   **Amended 2026-11-05 (DO-884, during implementation):** (c) with no live `### Org-wide`
   heading, the fragment's lines go first, then `### User-specific` (moved up, or added), then
   the other live lines, so the next render finds both headings and changes nothing; a fragment
   block must start with `### Org-wide` and hold no `### User-specific`, or the render exits 2.
   (d) A hook path may also be spelled `${HOME}/…` or `~/…`. (e) The no-marker check comes
   before the jq check, so `./install` (which runs `--apply` everywhere) exits 0 on a host with
   neither. The rules as built, the verbs and the backups: `docs/CLAUDE_SETUP.md`, "Rendered
   settings".

`herdr-claude-wire.sh` keeps the herdr skill regeneration and `herdr integration install`,
and its statusLine/bell merge becomes a call to the renderer. dotfiles-local's
`claude-hooks-wire.sh` is retired in favour of the overlay. The account-dir builder keeps
copying the rendered file into each seat dir on launch, so the laptop needs no new step.

### D5. Plugins are declared, installed headlessly

`enabledPlugins` + `extraKnownMarketplaces` in the rendered settings are the declaration.
The sync's plugin row (dev-sync's `here_plugins`, generalised) adds missing marketplaces
over HTTPS, installs every enabled plugin that is not installed (`claude plugin install
<name>@<marketplace> --scope user`, outside any account dir), updates stale ones on the
weekly cadence, and sets superseded entries to `false`. Per-project toggles
(`chrome-devtools-mcp`, `desktop-commander`) stay in the repos' own `.claude/settings`.
Docs (`plugins/install.md`, `loading.md`): a user-scope `true` plus a declared marketplace
is fetched in the background on a new machine; the plugin state files hold absolute paths
and are regenerated per host, never copied; `owner/repo` sources try SSH first, so the
host profile exports `CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1` on hosts whose GitHub auth is gh
over HTTPS (dev, sol-build). MCP servers reach every host through plugins (`linear-key`,
slack, notion, github); there is no shareable user-scope MCP file, and claude.ai connectors
follow the account (none on dev's token).

### D6. Skills and hooks: tracked, or regenerated from the host's own binaries

- Tracked: `rabota`, `run-later` (public), `zvi-voice` (private), comms hooks (private;
  vendored from `~/Projects/voiceprint` with a provenance line, or a submodule).
- Regenerated by the sync on each host, from that host's binaries: `herdr` (`herdr --skill`,
  as `herdr-claude-wire.sh` does) and `spawn` (`herdr-draft skill`), so the spawn skill's
  binary path is the host's, not `/home/zvi/...`.
- Retired or kept as the audit (D0) decides: `~/.claude/hooks/block-stop-on-live-lanes.sh`
  (unregistered, unreferenced); dev's `review-pr` skill copy and its 15 `~/.claude/agents`
  from 2025 (anything kept moves into dotfiles-local as a linked agent or skill).

### D7. Memory: one private repo, keyed by repo identity, synced both ways

**Store.** One private memory repo per tenant boundary (Q1), each checked out at
`~/.local/share/claude-memory/<tenant>` only on the hosts that serve that tenant:

| store | holds | checked out on |
|---|---|---|
| work (under the `zvi-quantivly` identity) | `repos/quantivly/<repo>/`, `dirs/` under `~/quantivly` | laptop, dev |
| personal (under `ZviBaratz`) | `repos/zvibaratz/<repo>/` (nanoclaw, herdr-draft, toysim …), `dirs/` under `~/Projects`, `~/toysim`, `~` | laptop, sol-build |

```
repos/<owner>/<repo>/      one dir per git remote (owner/repo lowercased, as dev-sync's
                           repo_of_url does), holding MEMORY.md + topic files
dirs/<slug>/               non-repo working dirs (today: ~/, ~/Projects, ~/quantivly/handoffs …)
.gitattributes             MEMORY.md merge=union
```

The tenant of a checkout is answered by the tenants file's route (`tenants.route`, the
one home for that fact), so the link script never keeps its own owner → tenant table.
Cross-repo memories about Zvi do **not** live in either store: see "User memories".

**Linking.** New `scripts/claude-memory-link.sh` walks the host's checkouts (the two
dotfiles repos, `~/quantivly/*`, `~/Projects/*`, `~/toysim/*`; herdr worktrees already
resolve to their main checkout's key), computes each one's Claude project key from its
path (`/` and `.` → `-`), and makes `<config>/projects/<key>/memory` a symlink into
`repos/<owner>/<repo>/`. A pre-existing real `memory/` is merged in (file union; the
`MEMORY.md` index unioned, the rule `docs/CLAUDE_ACCOUNTS.md` already uses for split
repair) and then replaced by the link. `--check` lists checkouts whose memory is not linked.

Why a symlink and not Claude Code's own knobs (docs read 2026-11-04, `memory.md`,
`env-vars.md`): the docs state auto memory is "machine-local… not shared across
machines" and offer no export or import. `autoMemoryDirectory` (any settings scope,
absolute or `~/` path) replaces one project's `memory/` dir, so using it means a settings
file per repo (team repos included) and it is undocumented whether a single user-level
value is shared by every project. `CLAUDE_CODE_PROJECT_DIR_NAME` keys a session's
`projects/` entry by a name of your choosing, but only with `CLAUDE_CONFIG_DIR` set and
only from the launching environment, so a bare `claude` from a plain shell silently
creates a second, path-keyed store. The symlink is launcher-independent and works on
every version; the doctor's "a real `memory/` where a link belongs" row catches the
split either way.

**Sync.** New `scripts/claude-memory-sync.sh` + `claude-memory-sync.timer` (every 10 min,
all hosts, `Persistent=true`), once per checked-out store: stage everything, refuse the
commit if any staged line matches the secret shapes in `scripts/redact-secrets.sh`,
commit as `<host>: <n> files`, `pull --rebase`, push. A conflict on a topic file keeps
both as `<name>.<host>.md` and the doctor names it. Nothing here reads a credential.
Remotes are HTTPS. On dev and sol-build the push uses the host's file-based gh token, as
dev's lanes already push. On the laptop (Q4) the unit pushes through gh's keyring
credential and, when the keyring is locked or the laptop just resumed, skips quietly;
the doctor row reports the age of the last successful sync with a laptop threshold of
2 h rather than 1 h, and no token is written to disk for it.

**Amended 2026-11-06 (DO-891):** eight amendments, from the plan
`docs/superpowers/plans/2026-11-06-claude-memory-stores.md`. Where they differ from the text above,
they win. M7 reverses a recorded answer; Zvi confirmed it on 2026-11-08.

- **(M1) Stores are a table, not one per tenant.** `memory-stores.json` names each store, its
  `remote` and the `tenants` it holds. A store is checked out at
  `~/.local/share/claude-memory/<store>`. A key maps to the store whose `tenants` holds the tenant
  `scripts/tenant-route <dir>` answers.
- **(M2) Store-relative directory.** A checkout with an `origin`: `repos/<owner>/<repo>`, lowercased,
  by the rule of `repo_of_url` in `scripts/dev-sync`. A directory with no `.git`, or a repo with no
  `origin`: `dirs/<slug>`, where slug is the path relative to `$HOME` with `/` → `-`, lowercased, and
  `home` for `$HOME` itself.
- **(M3) Keys.** The project key of a path is the path with every character outside `[A-Za-z0-9]`
  replaced by `-` (`/home/u/.dotfiles` → `-home-u--dotfiles`). This reproduces every live key on the
  laptop that still resolves to a directory; no directory there shows what `_` becomes, so that case
  is unverified. A worktree of an ordinary repo has no key of its own: Claude Code keys it by the
  main checkout. A submodule has **two** keys: its own path (sessions started in it), and its git dir
  `<super>/.git/modules/<name>` (sessions started in a worktree *of* the submodule, whose common dir
  is that git dir). Both link to one store directory.
- **(M4) Conflict copies** are named by inserting `.conflict-<host>` before the final extension
  (`x.md` → `x.conflict-<host>.md`; no extension: appended), not `<name>.<host>.md` as above, so a
  glob finds them without a host list. An existing copy with a different body is never overwritten:
  the next free `.conflict-<host>.2`, `.3`, … is used.
- **(M5) What gets a link.** A candidate is linked when it has a real `memory/` directory, **or**
  when its mapped store directory already holds a file (memory another host wrote). Nothing is
  created for a checkout with neither.
- **(M6) The secret gate withholds files, it does not refuse the commit.** A file whose content
  changes under the redactor's shape rules is left uncommitted and named; the other files sync.
- **(M7, confirmed by Zvi on 2026-11-08) Auth on a host with more than one GitHub account reads
  the routed token file.** This section and the answer recorded as Q4 say "keyring via gh, no token on
  disk". The keyring is keyed by host and cannot choose an account (`docs/GH_ACCOUNT_ROUTING.md`), so
  the sync asks `scripts/gh-route` and reads the shell's existing token cache file, as the
  `rabota schedule` tick does. No new token file is created. This reverses a recorded answer; Zvi
  confirmed it on 2026-11-08 ("Yes, as recommended").
- **(M8) Merge, never rebase.** This section says `pull --rebase`. A rebase removes every unpushed
  file from the working tree while it replays, and a session writing in that window stops it in a
  state `--abort` cannot leave (probed). The sync integrates with one `git merge`.
